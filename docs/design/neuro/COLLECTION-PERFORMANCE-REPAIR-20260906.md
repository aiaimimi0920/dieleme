## 2. 分钟采样是否在全盘查询？怎样优化了？

原先“分钟增量”不是每分钟对所有商品按完成时间重新筛一遍，而是前端比较两次总数快照。
但获取快照时确实会执行多个全局 `COUNT / GROUP BY` 聚合，而且列表还有逐条补查最近来源的
N+1 查询。多个客户端或健康/状态请求叠加时，会重复做相同工作。这个担忧是合理的。

### 已实现并部署到 NAS

1. **共享统计缓存**：一个 API 进程内所有请求共用统计快照，15 秒 TTL，
   并发只加载一次；没有新请求就不会专门唤醒查询。暂停、挑战、认证和控制状态不缓存。
2. **共享分钟历史**：NAS 返回总数差值与实际 60–90 秒采样窗口。
   新打开窗口可复用 NAS 已有历史，不必每个窗口各等一分钟；冷启动尚无样本时不伪造增量。
3. **列表批量查询**：非空分页固定 3 条 SELECT（总数、当前页、批量最近来源），
   不再每条商品查一次 occurrence/job。空页仅 2 条。
4. **单项查询限制**：详情单项的最近 occurrence 查询补上 SQL `LIMIT 1`。
5. **错误不冒充实时数据**：刷新失败时保留旧快照并标记 stale；不把数据库失败显示成 0 个商品。

新桌面优先使用 NAS 的分钟快照；待采样显示简短的 `—`，悬停解释原因。
旧快照显示“统计暂未更新”。旧 API 的前端采样回退仍保留，避免未升级后端时失效。

这次是**消除重复聚合和 N+1**，并没有谎称已经实现数据库事务级增量计数。
聚合本身仍可能扫描表或索引；如果未来负载需要进一步优化，再设计事务计数器/汇总表和
校准机制，不能为一个界面刷新直接引入未经验证的数据迁移。

### 线上证据

- 连续两次请求返回相同 `generated_at`，证明命中同一快照。
- 超过 TTL 后 `generated_at` 前进，证明不是永久缓存。
- NAS 返回有效、非 stale 的 62–72 秒窗口以及真实 `[0, 0, 0]` 增量。
- 本次观察到后续请求约 11 / 13 / 28 ms；这是少量请求实测，不是完整压力测试或稳定 SLA。
- PostgreSQL 上的真实条目接口成功返回 10 条；离线 SQL 计数测试覆盖 1 / 10 / 20 条分页，
  均为 3 条查询，保留“优先非归档来源、否则回退”的原有语义。

## 4. 能否把采集配置移到设置，并自动应用线上？

**可以，而且理解你的目标：设置页应是实际运行配置的控制入口，而非只在本地保存几个值。**

这项完整功能本轮尚未实现，没有放一个不具备线上应用能力的假表单。
已经核对字段、节点职责和当前控制器的限制，方案见
[采集设置统一管理](COLLECTION-RUNTIME-SETTINGS-PROPOSAL.md)。

最重要的几点：

- Worker 数量、单条重试与批次上限、单条延迟与轮询间隔，需要分别建模。
- “挑战失败 N 次后唤起 PC1”需要新的去重计数策略，不能套用 solver 冷却阈值。
- 修改环境变量后，单纯 `docker restart` 不会加载新值，需要受控重建受影响的容器；
  修改参数通常不必重新构建镜像。
- AI 密钥只写不回显，不进日志；实际推理测试通过才显示可用。
- 保存、应用中、节点已生效、失败回滚和结果未确认必须区分。
- 需要先解决安全控制通道。现有 NAS SSH 转发被拒绝，本轮未擅自改 SSH 策略，
  也未让管理令牌或 AI 密钥走未经确认的远程明文通道。
