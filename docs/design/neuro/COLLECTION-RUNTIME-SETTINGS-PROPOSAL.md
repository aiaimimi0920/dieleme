# 采集设置统一管理：实现边界与落地方案

状态：2026-09-06，已核对现有代码和部署契约；这是待实施方案，不是已上线功能。

## 目的

设置页应当成为 NAS、PC2、PC1 的统一采集运行配置入口，而不是另一份本地表单。
操作员在这里查看实际生效值、修改参数、测试 AI 连接，然后点击“保存并应用”。
程序自动把变更应用到对应节点，并展示节点回执。无需再手工找环境文件或敲部署命令。
不在每次输入一个字符时重启服务。

## 设置页分组与真实字段

| 分组 | 用户可调内容 | 当前实现与注意事项 |
| --- | --- | --- |
| API 连接 | NAS API 地址 | 桌面默认 `http://192.168.15.200:8001`，保留环境变量覆盖 |
| Worker | 链接、详情、AI 归档各自的数量 | 当前 Debian PC2 是固定 Compose 服务，实际为 1 / 3 / 4；不是改 Windows 启动器的数量变量 |
| 采集节奏 | 空闲轮询、活跃批次间隔、单条成功间隔、失败退避 | 需分开显示，不能用一个“采集间隔”覆盖不同语义 |
| 重试 | 单条商品最大尝试次数、批次尝试上限、失败冷却 | `FAPAI_DETAIL_ITEM_MAX_ATTEMPTS` 才是单条上限；`FAPAI_DETAIL_MAX_ATTEMPTS` 是一批的上限 |
| 人工认证 | 连续挑战失败 N 次后唤起 PC1、停滞兜底、通知冷却 | 需要增加明确的失败计数策略；不能把已有 solver 冷却阈值冒充人工认证阈值 |
| AI 连接 | Base URL、API Key、主模型、候选模型、超时、请求重试 | 复用当前 OpenAI-compatible 适配器；密钥只写不回显；测试必须包含实际推理 |
| 应用状态 | 期望版本、各节点生效版本、应用进度、失败原因 | “保存成功”与“线上已生效”必须分开 |

已抽查的实际定义：

- `tools/seed_collector_config.py`：`FAPAI_SEED_LOOP_INTERVAL_SECONDS`、活跃批次间隔。
- `tools/detail_worker_config.py`：详情批次/单条上限、成功间隔、失败退避、挑战冷却。
- `src/llm_openai_compatible.py`：`OPENAI_BASE_URL`、`OPENAI_API_KEY`、`OPENAI_MODEL`、
  `OPENAI_MODEL_CANDIDATES`、`OPENAI_TIMEOUT_SECONDS`、`OPENAI_MAX_RETRIES`。
- `docker-compose.nas-central.yml`：NAS 认证恢复的停滞阈值、PC1 / PC2 超时和冷却时间。
- `docs/runbooks/collection-engine-restart.md`：当前控制器只接受固定 Worker 重启，
  不接受任意命令、配置、服务名或宿主路径。

当前分析适配器明确限制为非 GPT / Codex 模型路由。设置页应显示并复用该校验，
不能让表单保存一个后台必然拒绝的模型；若需要改变模型政策，应单独评审。

## 为什么不能“写 env 后 docker restart”

现有容器的环境变量在创建时已经固定。修改宿主环境文件后，仅执行 `docker restart`
不会让旧容器获得新环境变量。

- 只改变间隔、重试、AI 参数：使用原有镜像，受控重建受影响的 Worker 容器。
- 改变 Worker 数量：生成受限的服务配置并进行增减、租约收尾和健康检查。
- 改变 NAS 认证策略：NAS 自身要么支持配置热加载，要么由宿主控制器安全重建 API。
- 只改变参数通常不需要重新构建镜像；新增程序能力才需要新镜像。
- 原有“重启”按钮仍保留其狭窄职责，不偷偷扩大为任意部署入口。

## 最小完整实现链路

1. **NAS 配置契约**：白名单字段、类型/范围校验、版本号、并发修改检查；
   返回实际生效值和期望值。未知字段直接拒绝，不允许提交任意 env 或 shell。
2. **安全存储**：普通配置与秘密分离。密钥保存到受限秘密文件，响应只返回“已配置”。
   空白密码输入表示不修改；清除密钥必须是单独的明确操作。
3. **保存并应用队列**：持久化请求 ID、配置版本和状态，重复点击幂等。
   密钥不得出现在公开队列、审计记录、错误详情和命令参数中。
4. **节点控制器**：PC2 从 NAS 领取白名单任务，在宿主执行；使用固定项目、已核实挂载和
  受管服务模板。NAS 自身更新需要独立的宿主执行边界，不能让 API 容器自己操作整个 Docker。
5. **应用事务**：校验新配置 -> 备份旧配置 -> 渲染并检查 Compose -> 重建受影响服务 ->
   验证容器健康、实际环境配置版本、业务探针 -> 回写各节点结果。
6. **失败处理**：保留旧配置/镜像，失败时回滚配置和服务定义；超时或断线显示“结果未确认”，
   不自动重复执行重建，更不能恢复旧数据库去“回滚”。
7. **PC1 认证策略**：同一挑战的真实失败结果按 ID 去重计数，轮询不增加次数。
   达到阈值只发起一次认证事件；复用可见的专用认证浏览器，不恢复每几分钟重复弹框。
8. **桌面页**：固定左下角“设置”，按上述分组展示；保存前列出受影响节点及是否短暂停机。
   收到正确版本的节点回执后，才显示“已应用”。

AI 测试需验证聊天/推理响应及最小语义结果。此次线上 `/models` 可以成功，但实际聊天接口
返回 503，说明“模型列表可访问”不能作为 AI 可用的验收标准。

## 不丢数据的验收条件

- 不执行 `down -v`、数据库重建、删除数据目录或从旧备份覆盖线上数据库。
- Worker 调整保留已有浏览器配置、Cookie、采集产物和数据库挂载。
- 修改数量时，先停止该 Worker 领取新任务，再处理在途任务/租约；不复制正在执行的任务。
- 自动化测试覆盖字段校验、秘密脱敏、并发修改、幂等、拒绝任意命令、故障回滚与回执伪造。
- 本地/隔离测试通过后，再验证真实节点生效版本与业务行为；健康状态不能代替商品增长。
- 每次部署分别报告源码、构建产物、节点部署、配置生效和业务结果，不能混成一个“成功”。

本轮未创建上述配置读写 API、设置表单或应用控制器，因此不能把它们列为已交付。
