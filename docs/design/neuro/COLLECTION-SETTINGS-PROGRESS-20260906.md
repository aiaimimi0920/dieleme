- AI 地址、模型路由、超时、请求重试次数，以及留空保留的 API Key。

NAS 接口使用独立的配置版本、请求 ID 和单操作队列；PC2 控制器持久化回执后才操作容器，
只重建受影响 Worker，固定当前镜像和挂载，失败时尝试回滚并验证。数据库和浏览器不在
配置重建范围内。配置请求被接受、容器健康、AI 推理成功是三个不同状态，不混为一谈。

安全和并发保护包括：拒绝远程明文 HTTP 传密钥、操作员/代理分权、密钥不回显、提交后清空
密钥输入、切换连接或授权使旧表单失效、旧请求响应不能覆盖新连接、未知结果阻止再次提交。

## 3. 为什么本轮没有直接打开线上“保存并应用”

以下是明确的未完成项，而不是已部署功能：

1. **安全通道待确认。** NAS 当前拒绝 SSH 转发。已询问是否允许为 PC2 控制账号设置仅通向
   NAS `127.0.0.1:8001` 的受限转发，尚未收到答复；PC1 编辑器同样需要安全控制入口。
2. **真实配置存在漂移。** 根据实际容器标签确认正确入口为 release 下的
   `ops/pc2-linux/compose.yaml`，不是根目录的旧 `docker-compose.collection.yml`。
   正确模型确实为 1 个链接、3 个详情、4 个分析和 1 个浏览器服务。同阶段参数一致，
   镜像和 bind 挂载匹配；但链接/详情容器的 `OPENAI_MODEL`、`OPENAI_MODEL_CANDIDATES`、
   `OPENAI_REASONING_EFFORT` 与部署文件不同。当前控制器因此拒绝覆盖，需要先审定真实基线。
3. **重启控制器需要协调。** 旧实现固定重启 8 个 Worker，尚未与动态数量及新控制器共享锁；
   不能直接同时启动。当前线上重启按钮仍不可用。
4. **跨版本持久化尚未接入。** 新控制器保存 `active.json`，但现有部署脚本尚不会继承它；
   必须避免下一次镜像部署覆盖已保存配置。
5. **人工认证失败次数阈值尚未实现。** 界面明确标注不可配置，继续保留现有认证策略。

详细协议、回滚、权限和激活门槛见 [运行设置说明](../../runbooks/collection-runtime-settings.md)。
