1. 在 Crow 点击认证，弹窗没有二级标题、说明段落、URL 编辑框或“提交认证任务”。

可以用 Escape 或点击弹窗外部关闭弹窗；关闭不会取消已经提交的 PC2 交接，重新打开可以继续查询。遇到网络错误时再次点击“已完成挑战”会查询已有任务，而不是重复导出 Cookie。

## 修复了什么

### 旧流程的问题

- 打开认证弹窗就调用通用暂停接口，把运行状态标记成操作者暂停，容易与 NAS 自动恢复的保护条件冲突。
- “提交认证任务”没有建立真正的跨机器交接任务。
- 导出失败、会话尚未通过复用验证等情况被包装成笼统的“开始失败”；前端也没有正确等待 PC2 的恢复结果。
- 旧 URL 规范化逻辑把商品详情挑战转换成列表页，用户可能在错误的页面上完成认证。
- 已有后台 PC1 任务时，直接等待旧任务可能仍然检查旧标签页，而不是用户刚刚完成的页面。

### 新交接的保护边界

- 人工完成请求需要既有恢复凭据，并核对当前挑战 ID；已有挑战时，缺失或过期的挑战身份不能修改当前任务。
- 尚未发布快照的后台任务可以由人工完成操作接管：创建新的恢复 ID，使旧后台任务的迟到发布失效。
- 已进入 PC2 接收或验证阶段的任务不重复接管、导出或重启。
- PC1 使用跨进程文件锁；多个桌面实例不能同时执行 Cookie 发布。
- 人工快照按恢复 ID 和 SHA-256 独立保存。发布失败或旧任务迟到不会覆盖正在使用的标准 Cookie 文件。
- PC2 继续通过原有受保护接口取快照、验证摘要、导入浏览器会话并确认恢复；没有绕过站点挑战，也没有自动解题。
- Cookie 只在认证助手和既有交接协议内处理，不回传到前端状态文本、源码或交付报告。

本次复用的是现有 Cookie 快照协议，不是复制整份浏览器 Profile。第三方站点可能绑定 IP 或设备；如果会话无法跨设备复用，程序会保留等待或失败状态，不会假装已经通过挑战。
