## 查明并修复的原因

### 1. 历史镜像版本账本未同步，控制器拒绝执行

PC2 实际浏览器、链接和分析 worker 的镜像已更新，但控制器 `active.json` 仍保存旧镜像摘要。控制器正确地将此视为运行环境漂移并拒绝继续；统一循环先处理设置，再处理重启，因此两条控制通道都受到影响。

新增 `tools/pc2_settings_reconcile.py`，只允许经过核验的镜像版本对账：

- 在共享操作锁下检查预期镜像、服务、健康状态、环境变量和挂载。
- 不接受非镜像漂移，不忽略未决操作，不自动重放未知结果的请求。
- 保留旧账本和校验信息后更新镜像摘要，不修改业务参数或数据。

已经对线上账本完成受控对账。此后真实设置请求可以正常获得终态。
以后若绕过设置控制器直接发布新镜像，仍必须完成这一步，不能把漂移校验直接关闭。

### 2. 重启命令的固定超时不足以覆盖旧 Docker 的串行停止

解除账本阻塞后进行真实重启验收，又复现了独立问题：旧 Docker 客户端对一串容器 ID 串行执行重启，每个 worker 最多等待 30 秒退出，而控制器对整个命令只给了 120 秒。

首次验证中只有分析 worker 陆续重启，详情和链接 worker 尚未轮到就触发超时，诚实返回 `controller_interrupted`，而不是成功。

修复 `tools/pc2_engine_controller.py`：对已核实身份的 worker 分别执行重启，最多 8 个并发，每个命令有 60 秒截止时间，随后仍逐个检查原容器身份、新的启动时间和健康状态。没有扩大允许重启的服务范围，浏览器、Docker 守护进程和 NAS 不在重启名单内。

修复后重新部署 PC2 主机控制器，并以一个新的验证请求完成验收。没有重放旧请求，也没有伪造旧请求的成功回执。

### 3. NAS 的旧单例状态覆盖了独立链接挑战状态

NAS API 重启后，旧的全局 solver 单例可以处于 `idle`，但 seed/detail 各阶段的持久化挑战仍存在。原状态接口在这种情况下把阶段的 `challenge_id`、暂停和人工认证标志清空。

因此 Crow 从状态接口读到空 ID，而提交认证的接口读取真实阶段状态，二者不一致，实际返回 **HTTP 409 `challenge_changed`**。

修复 `src/server_auth_recovery.py`：状态接口始终返回各阶段自己的持久化状态，不再用旧单例的空闲状态抹掉阶段挑战。新增回归测试覆盖 API 重启后的独立阶段身份和暂停标志。

部署此修复后，同一个真实 PC1 人工认证流程可以完成 NAS 到 PC2 的交接。

### 4. 分阶段认证不应强制重启共享浏览器

原流程导入 Cookie 后强制重启浏览器，旧版实测一次交接约 156 秒，并出现浏览器重启次数增加。现在 seed/detail 认证在导入 Cookie、确认服务端阶段转换成功后，直接进行阶段验证，不再通过浏览器重启推动状态机。

同时修复了阶段转换响应未检查和同一轮可能重复导入的问题。验证失败和验证服务不可用有明确失败原因，不再一直显示正在重启浏览器。旧的无阶段兼容流程未冒充新的分阶段协议。

### 5. 本机等待增加明确截止时间

- 原生设置助手：总执行时间 35 秒。
- 原生认证助手：总执行时间 180 秒。
- 前端设置原生调用：40 秒。
- 设置操作轮询：12 分钟上限，保留用户编辑内容和待核实操作信息，不自动重放。

这些是防止无限等待的保护措施，不代替对线上故障根因的修复。
